# HFM-3D 4xH200 DDP 训练方案

## 目标

让 `models/mf-generators/hfm_3d/train.py` 支持通过 `torch.distributed.run` 在 4 张 H200 上进行 DDP 训练，并同步更新 `docs/corearchitecture-v2-phase-d-runbook.md` 中 D1 的后台训练命令。

不改变 HFM-3D 的模型结构、loss 语义、输入数据格式和 checkpoint 字段含义。

## 当前调用链分析

### 入口

当前唯一训练入口是：

```text
models/mf-generators/hfm_3d/train.py
```

调用链：

```text
CLI args
  -> sys.path 注入 workspace 包路径
  -> HUMUMoleculeEncoder(dim=args.dim)
  -> LorentzFlowMatching(dim=args.dim, n_steps=args.n_steps)
  -> local nn.Sequential decoder
  -> _load_molecules(args.data)
  -> Python list 按 args.batch_size 切片
  -> encoder.encode(smiles)
  -> flow_model(x0, x1)
  -> decoder(x1)
  -> AdamW.step()
  -> _save_ckpt(...)
```

### 数据流

`_load_molecules()` 从 `*.jsonl` 或 `manifest.json` 的 `shards` 读取样本，返回 `list[dict]`。训练循环直接按列表下标切片，每条样本要求包含 `smiles`。

当前没有 `Dataset`、`DataLoader`、`DistributedSampler`。如果直接用 `torchrun --nproc_per_node=4 train.py`，4 个进程会读取同一份完整样本、重复训练、同时写同一路径 checkpoint。

### 模型与状态

训练状态包含：

- `flow_model.state_dict()`
- `decoder.state_dict()`
- `optimizer.state_dict()`
- `epoch`
- `loss`

`HFM3DGenerator.load_checkpoint()` 当前读取的是 `model` 或 `decoder` 字段；而训练脚本保存的是 `flow_model` 和 `decoder`。本次只处理训练 DDP，不改变 generator 加载契约，避免扩大范围。

### 错误传播

当前脚本缺少显式数据校验。若数据目录为空，训练循环不会报错，最终会保存 `best_loss=inf` 的 checkpoint。这是 DDP 改造必须顺手修正的真实问题，否则 4 卡后台训练可以静默产出无效权重。

### 并发控制

当前无并发控制。DDP 需要：

- 从 `RANK`、`WORLD_SIZE`、`LOCAL_RANK` 读取分布式上下文。
- CUDA 下使用 NCCL，CPU 测试下使用 gloo。
- 每个 rank 绑定本地 GPU。
- 用 `DistributedSampler` 划分样本。
- 只允许 rank 0 创建最终业务 checkpoint 文件。
- 训练结束和异常路径清理 process group。

## 方案选项

### 方案 A：在现有 `train.py` 内兼容单进程与 DDP

直接让 `train.py` 自动识别 `WORLD_SIZE>1`，单进程路径保持原命令可用，DDP 路径由 `torch.distributed.run` 驱动。新增 `run_hfm_4h200_background.sh` 只负责启动和日志/PID 管理。

优点：

- 改动范围最小。
- 不创建并行训练实现。
- 用户已有单卡命令不失效。
- runbook 能给出真实后台命令。

缺点：

- `train.py` 会比现在长，需要拆小 helper 保持可读。

### 方案 B：新增独立 `train_ddp.py`

保留 `train.py`，新增 DDP 专用入口。

优点：

- 单卡脚本不动。

缺点：

- 违反单一实现原则，训练逻辑会复制。
- 后续单卡/DDP 容易行为漂移。

### 方案 C：只新增 shell 脚本包一层 `torchrun`

不改 `train.py`，只用后台脚本启动多进程。

优点：

- 改动最少。

缺点：

- 会重复训练全量数据并产生 checkpoint 写竞争，不能满足真实 DDP。

推荐方案：方案 A。

## 设计

### `train.py` 内部结构

新增轻量内部组件：

```text
DistributedContext(enabled, rank, world_size, local_rank)
MoleculeDataset(samples)
_distributed_context_from_env()
_setup_distributed(...)
_cleanup_distributed(...)
_is_main_process(...)
_build_dataloader(samples, args, distributed)
_unwrap_model(model)
_reduce_loss_sum(loss_sum, batch_count, device, distributed)
```

核心流程：

```text
main()
  -> parse args
  -> add project paths
  -> distributed = _distributed_context_from_env()
  -> device = _get_device(args, distributed)
  -> _setup_distributed(distributed, device)
  -> build encoder / flow_model / decoder
  -> wrap flow_model 和 decoder with DDP when distributed.enabled
  -> samples = _load_molecules(args.data)
  -> if not samples: raise ValueError
  -> dataloader = DataLoader(MoleculeDataset(samples), sampler=DistributedSampler(...))
  -> for epoch:
       sampler.set_epoch(epoch)
       for batch:
           encode smiles with no_grad
           compute flow_loss + recon_loss
           backward + optimizer.step
       all-reduce epoch loss sum/count
       rank 0 log/save
  -> rank 0 save final
  -> cleanup distributed
```

### Checkpoint 兼容

保存字段保持：

```text
epoch
loss
flow_model
decoder
optimizer
```

DDP 保存时使用未包裹模型：

```python
_module(flow_model).state_dict()
_module(decoder).state_dict()
```

恢复时先 load 到原始模型，再 wrap DDP，避免 `module.` 前缀污染。

### 日志与后台脚本

新增脚本 `run_hfm_4h200_background.sh`，风格对齐 `pipelines/humu_pretrain/run_humu_4h200_background.sh`：

- `HFM_DATA_DIR` 必填。
- `HFM_OUTPUT_DIR` 必填。
- `PYTHON_BIN` 默认 `$PROJECT_ROOT/.venv/bin/python`。
- `NPROC_PER_NODE` 默认 `4`。
- `CUDA_VISIBLE_DEVICES` 默认 `0,1,2,3`。
- `RUN_NAME` 默认 `hfm_4h200_<utc timestamp>`。
- 写入 log、pid、manifest。
- 如果 pid file 指向运行中进程，直接失败。

启动命令内部使用：

```bash
$PYTHON_BIN -u -m torch.distributed.run \
  --standalone \
  --nproc_per_node="$NPROC_PER_NODE" \
  models/mf-generators/hfm_3d/train.py \
  --data "$HFM_DATA_DIR" \
  --output-dir "$HFM_OUTPUT_DIR" \
  ...
```

### 测试

新增或扩展单元测试：

1. 小 JSONL CPU 训练一轮，确认：
   - 返回码为 0。
   - `best_model.pt` 存在。
   - `final_model.pt` 存在。
   - checkpoint 中有 `flow_model`、`decoder`、`optimizer`。
2. 空数据目录训练失败，stderr 包含空数据错误。
3. 不在单元测试中启动 4 GPU DDP。DDP 运行命令写入 runbook，由真实 H200 环境执行。

## KISS 四问

1. 这是现实问题还是想象问题？
   - 现实问题。当前 runbook 明确 D1 仍不能 4xH200 DDP；直接 `torchrun` 会重复数据和 checkpoint 写竞争。
2. 有没有更简单的做法？
   - 最简单可用做法是在现有 `train.py` 内兼容 DDP，不创建并行版本。
3. 会破坏什么？
   - 风险是单卡训练行为变化。控制方式：保留原 CLI 参数，`WORLD_SIZE=1` 时仍走同一训练语义；新增 CPU smoke 覆盖。
4. 当前项目真的需要这个功能吗？
   - 需要。阶段 D 第一项明确是 HFM-3D 真实预训练（ChEMBL 34 + 4xH200）。

## 性能影响

- DDP 后每个 rank 只处理本 rank shard，避免 4 进程重复全量数据。
- epoch loss 用 `all_reduce` 汇总 sum/count，日志只在 rank 0 输出。
- `encoder.encode()` 仍逐条执行，这是现有训练入口的真实瓶颈。本次不改为批量 encoder，避免同时改变训练语义。
- DataLoader 初版使用 `num_workers=0`，避免 dict batch 和 RDKit 对象跨进程复杂性；后续如需优化再显式增加参数。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| DDP checkpoint 保存 `module.` 前缀 | 保存前统一 `_module(model).state_dict()` |
| 非 rank 0 同时写 checkpoint | 只允许 main process 保存 |
| 某 rank 数据为空 | `DistributedSampler` 会按副本数补齐；总样本为空时 fail-fast |
| torch distributed 初始化失败 | 后台脚本先检查 Python、数据目录、输出目录；训练脚本异常后清理 process group |
| 单卡命令被破坏 | 保留原参数和单进程路径，新增 CPU smoke |
