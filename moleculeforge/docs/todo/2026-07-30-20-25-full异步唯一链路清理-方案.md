# Full 异步唯一链路清理方案

## 目标

将已经通过集成验证的 `full + async orchestrator-svc` 设置为项目唯一默认执行骨架，迁移 UI 到规范接口，删除并行工作流、同步入口、gRPC 入口和旧 API 兼容层。现有 full 业务链路不重写，只删除分支并收紧调用入口。

## 实际调用链

规范入口和运行链如下：

```text
Browser UI
  -> API Gateway /v1/orchestrator/*
  -> orchestrator-svc async REST API
  -> RunStore 创建持久化任务
  -> 后台 asyncio task
  -> full WorkflowGraph
  -> Redis AgentRequestClient
  -> nl2obj
  -> generator_coord -> generator_router -> generators -> teacher feedback
  -> validation
  -> retrosyn -> supply -> SRB compile
  -> critic
  -> SRB execution
  -> provenance
  -> RunStore 状态、事件和结果
```

运行控制继续使用现有异步接口：

- 创建任务
- 查询任务列表和快照
- 查询阶段事件
- 暂停和恢复
- 外部证据恢复
- 取消任务
- 查询项目和结果

## 已验证事实

- `orchestrator-svc` 已实现持久化异步创建、后台执行、状态转换、事件记录、暂停、恢复、外部证据恢复和取消。
- `FullWorkflowClients` 已接通 nl2obj、生成器协调、分级验证、逆合成、供应、SRB、critic、执行和 provenance。
- `WorkflowGraph` 的 full 分支已包含 planning、generating、validating、retrosyn、critic、executing、refining、escalating、validation_error 和 awaiting_evidence。
- 集成测试已使用 `FullWorkflowClients` 和 full `WorkflowGraph` 验证完整消息流、身份关联、反馈和下游阶段。
- 当前项目仍同时保留 state_only、engineering、同步 Python、gRPC、OrchestratorAgent、ReasoningPipeline、mvp_pipeline 和旧网关路由。
- 当前 UI 虽然从 `/v1/orchestrator/design` 提交任务，但仍通过 `/v1/design`、`/v1/reason` 和 `/v1/stream` 读取状态、历史和事件。

## 唯一默认行为

### Orchestrator

- `orchestrator-svc` 只接受 full 请求。
- `workflow_scope` 不再用于选择执行分支。外部请求可以不再提供该字段，服务内部状态固定记录为 `full`，用于已有智能体消息契约和持久化数据识别。
- `validation_passed` 不再由创建请求伪造，验证结果只由 Validation Agent 返回。
- `WorkflowGraph` 只构建 full 图，不再接受 scope 参数。
- 证据恢复继续从 validating 节点进入同一 full 图。

### API Gateway

只保留规范 Orchestrator API：

- `POST /v1/orchestrator/design`
- `GET /v1/orchestrator/runs`
- `GET /v1/orchestrator/runs/{run_id}`
- `GET /v1/orchestrator/runs/{run_id}/events`
- `POST /v1/orchestrator/runs/{run_id}/pause`
- `POST /v1/orchestrator/runs/{run_id}/resume`
- `POST /v1/orchestrator/runs/{run_id}/evidence/resume`
- `POST /v1/orchestrator/runs/{run_id}/cancel`

这些接口只做认证、主体传递和 HTTP 代理，不包含第二套工作流实现。

项目管理和 Pareto 结果接口继续保留，因为它们分别服务于 full 请求上下文和 full 结果展示。独立的 molecule、predict 和 route 领域接口本次不修改，避免扩大清理范围。

### UI

- 删除工作流 scope 和 `validation_passed` 选择器，页面固定提交 full 请求。
- 增加 Bearer Token 输入。Token 只保存在当前页面内存，不写入 localStorage、sessionStorage、Cookie 或 URL。
- 所有 full 创建、列表、状态、事件和控制请求携带 `Authorization: Bearer <token>`。
- 不再使用不能设置 Authorization Header 的原生 `EventSource`。
- 使用现有事件查询接口按 `after_step` 增量轮询，同时轮询任务快照；不新增第二套 SSE 服务。
- 历史记录改用 `GET /v1/orchestrator/runs`。
- 任务读取改用 `GET /v1/orchestrator/runs/{run_id}`。
- UI 必须收集 full 契约要求的真实字段：
  - `project_id`
  - `nl_input`
  - `max_refinements`
  - `n_samples`
  - `generation_strategy`
  - `retrosyn_engine`
  - `validation_policy`
  - `teacher_policy`
  - `selection_policy`
- 不伪造生产策略默认值。`workflow_scope=full` 和 `teacher_source=hypseek` 属于唯一契约常量，不作为可选项展示；teacher version、KD 权重、验证阈值和选择标准由用户提供。
- 删除依赖 `/v1/reason/known` 的 Known Catalog 入口。本次不为已删除的兼容功能创建新 API。
- 结果面板继续从 full 快照中的 candidates、validation、retrosyn、supply、srb、critic 和 execution 数据渲染。
- 为 paused、awaiting_evidence、failed、interrupted、rejected 和 completed 状态提供真实状态展示；证据恢复使用规范接口。

## 删除范围

### 工作流分支

- 删除 `state_only` 图。
- 删除 `engineering` 图。
- 删除 `EngineeringWorkflowClients`。
- 删除工程链使用的本地 RDKit 随机生成、属性预测和兼容排序辅助函数。
- 将 `FullWorkflowClients` 改为独立类，只保留现有 full 方法。

### 并行入口

- 删除 `agents/orchestrator/src/orchestrator/agent.py`。
- 删除 Orchestrator Agent 插件注册。
- 删除 `agents/orchestrator/src/orchestrator/pipeline.py`。
- 删除 `pipelines/mvp_pipeline`。
- 删除 `orchestrator-svc.start_design()`。
- 删除 Orchestrator gRPC servicer、启动逻辑和 50071 端口。
- 删除 Orchestrator gRPC 请求、响应和 service proto；保留同一 proto 文件中 NL2Obj 实际仍使用的定义。
- 重新生成 proto 代码。

### 兼容 REST 入口

- 删除 `/v1/design/*`。
- 删除 `/v1/reason/*`。
- 删除 `/v1/stream/*`。
- 删除 orchestrator-svc 的 `/v1/orchestrator/{design_id}`、`/{design_id}/pause` 和 `/{design_id}/resume` 别名。

### 依赖和部署

- 删除 mvp pipeline workspace/source/dependency 声明。
- 删除只被 engineering Orchestrator 使用的 `mf-generators-rdkit-random`、`mf-oracles-rdkit-oracle` 和 `mf-retrosyn-aizynth` 的 orchestrator-svc 直接依赖；不删除这些独立模型包。
- 删除 orchestrator gRPC 运行依赖和部署端口 50071。
- 更新 Docker Compose、Kubernetes、Helm、测试路径、导入约束和 `uv.lock`。

## 保留范围

- full 图现有业务节点、路由和状态转换。
- RunStore、RunControl、异步后台任务和事件持久化。
- full validation policy、teacher policy 和 selection policy 严格校验。
- OIDC 验证、内部服务 Token 和 run owner 隔离。
- Redis AgentRequestClient 以及所有 full 链路领域智能体。
- 生成器、验证器、逆合成、供应、SRB、critic、执行和 provenance 实现。
- HUMU、生成器和 ICLM 等离线训练链路。
- 项目管理、Pareto、predict、molecule 和 route 独立领域能力。

## 执行顺序

1. 先补齐 API Gateway 的规范异步运行代理接口。
2. 将 UI 迁移到规范 full API、Bearer Token 和增量事件轮询。
3. 删除旧网关路由，验证 UI 不再引用兼容路径。
4. 固定 WorkflowGraph 和 orchestrator-svc 为 full。
5. 删除同步、gRPC、Agent、Pipeline 和 MVP 入口。
6. 清理 proto、依赖和部署端口。
7. 删除或调整对应兼容测试。
8. 更新锁文件。
9. 执行静态检查、单元测试、集成链测试、API/UI E2E 和部署配置核验。

## 验证标准

- 全仓库生产代码不再出现 `state_only` 或 `engineering` 工作流分支。
- 全仓库不再存在 `OrchestratorAgent`、`ReasoningPipeline`、`mvp_pipeline` 或 `start_design`。
- Orchestrator 不再监听或声明 50071。
- UI 不再请求 `/v1/design`、`/v1/reason` 或 `/v1/stream`。
- UI 创建请求始终进入 full 异步任务。
- UI Token 不写入任何持久化浏览器存储。
- 未认证 full 请求返回真实认证错误。
- 已认证用户只能查看和控制自己的 full 任务。
- full 任务能够完成或进入真实的 rejected、failed、interrupted、awaiting_evidence 状态。
- 外部证据能够通过规范恢复接口继续同一任务。
- full 集成测试继续覆盖从 nl2obj 到 execution/provenance 的实际控制流。
- Docker、Kubernetes 和 Helm 只暴露 orchestrator HTTP 8011。

## KISS 检查

1. 这是现实问题：项目存在多套实际可调用入口，UI 也依赖旧接口。
2. 更简单的做法：保留已验证 full 实现，只删除条件分支和包装层，不重写领域链路。
3. 会破坏的内容：旧 API、同步 Python、gRPC、OrchestratorAgent、MVP runner 和旧 UI 调用会被主动删除，这是本次明确目标。
4. 项目需要的功能：只保留完整分子设计主链及其运行控制，不新增新的编排能力。

## 风险与控制

- UI 认证失败：所有请求统一经过一个内存 Token Header 构造函数，并验证 401、403 和 503。
- EventSource 无法携带 Header：删除 EventSource，复用现有事件分页接口。
- 删除 engineering 后 full 类继承失效：先让 FullWorkflowClients 独立，再删除父类。
- 删除 scope 分支时误删 full 路由：以现有 full 集成测试中的阶段和 Agent subject 集合为回归基线。
- 删除 gRPC 时影响 NL2Obj proto：只删除 OrchestratorService 相关消息，保留 NL2Obj 定义并执行 proto 同步检查。
- 历史任务兼容：本次不保证 state_only、engineering 或旧 design 快照继续通过兼容 API 读取；数据库文件不主动删除。

## 性能影响

- 删除本地 engineering 计算和重复入口，不增加 full 链路模型调用。
- UI 事件查询使用 `after_step` 增量读取，避免重复下载全部事件。
- UI 快照轮询保持单任务、固定间隔，不增加并行请求风暴。
- Orchestrator 不再启动额外 gRPC server 和线程池。
